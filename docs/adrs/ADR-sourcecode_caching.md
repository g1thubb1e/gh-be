# BE 소스코드 캐싱

분야: 기술
상태: 판정중
작성자: 영 서

## 🎯 Context

<aside>
💡

- **API 제한:** GitHub API의 시간당 호출 제한이 5,000회로 설정되어 있어, 사용자 증가 시 안정적인 서비스 제공에 제약이 있음.
- **성능 격차:** 캐싱 미사용 시 응답 속도는 약 300ms이나, 캐싱 시 30ms로 **10배의 성능 향상**이 가능함.
- **운영 효율:** 현재 `git_diagram` 레파지토리 기준, 캐싱 미적용 시 하루 200건의 요청만 처리 가능하나, 캐싱 적용 시 500건 이상 처리가 가능하여 처리 용량이 2.5배 증가함.
- **리소스 소모:** 소스코드 데이터의 크기는 레파지토리당 수십 KB 수준(예: 40KB)으로 매우 작아 저장 공간 부담이 적음.
</aside>

## **🤝 Decision**

<aside>
💡

- **GitHub 소스코드를 DB에 캐싱하는것 제안**
- 단, 무분별한 저장 공간 비대를 방지하기 위해 **레파지토리당 캐싱 크기를 최대 1MB로 제한**하는 정책을 함께 도입
- 최초 Repo제시 시 tree API를 통해 메타데이터를 가져옴. git Diagram 로직에서 다이어그램을 형성하고 사용자와 챗봇과 대화에서 특정 파일에 대한 접근 필요가 발생 시 Contents API로 실제 파일에 접근. 이후 가져온 파일 정보를 LLM 에게 제공하며 가져온 파일 정보를 캐싱(RDB vs Object Storage)한다.
- **캐싱 만료 정책:** 캐싱된 데이터의 만료 판정은 [TTL and 변경] 으로 결정한다. TTL 시간은 N일(default 1)로 한다. 만료 시 다시호출할때 GitHub API를 통해 갱신한다.
- 캐싱 만료 변경 기준 : tree API에서 메타데이터를 가져올 때 파일마다의 SHA값도 같이 가져온다. 기존 캐싱된 파일의 SHA값과 treeAPI의 SHA가 다를 경우, 변경되었다고 판단한다.
</aside>

## **⚖️ Consequences**

### **👍 장점**

- **사용자 경험(UX) 개선:** 응답 속도가 300ms에서 30ms로 대폭 단축되어 실시간성에 가까운 인터랙션 제공 가능.
- **처리 용량 확대:** API 호출 횟수 최적화를 통해 하루 처리 가능한 요청 건수를 200건에서 500건으로 확대.
- **비용 및 시간 절약:** 하루 200건 처리 기준, 총 대기 시간을 60초에서 6초로 90% 절감 가능.
- **안정성 확보:** GitHub API 서버의 일시적인 장애나 레이트 리밋(Rate Limit) 상황에서도 캐싱된 데이터를 통해 서비스 지속 가능.

### **👎 단점**

- **데이터 정합성 문제:** 원본 소스코드가 수정되었을 때 DB에 캐싱된 데이터와 일치하지 않을 수 있음 (최대 하루정도 차이)
- **저장 비용 발생:** 캐싱 안 함 대비 약 8MB(하루 200건 기준 예상치)의 추가 DB 공간이 필요함.
- **관리 복잡도:** 캐싱 크기 제한(1MB)을 체크하고 초과 시 처리하는 로직을 서버 측에 구현해야 함.
- **관리 복잡도:** DB 설계 시 생성 시간(CreatedAt)을 기록하고, 조회 시 만료 여부를 체크하여 갱신하는 로직이 추가되어야 함.

### 고려할점

- **데이터 최신성 유지:** 1일 단위 만료 정책을 통해 최소 하루 한 번은 최신 소스코드로 동기화됨으로써 데이터 부정합 리스크 완화.
